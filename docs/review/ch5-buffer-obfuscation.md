## 0. 本章主线（先记住这三句）

1. **C/C++ 不做边界检查 + 栈向低地址增长** → 超长输入覆盖返回地址 → 崩溃或**控制流劫持**（执行任意代码）。
2. 防御是“多层叠加”：**W^X 让栈不可执行、canary 检测越界、ASLR 让地址不可猜**；每一层都有绕过方法，没有银弹。
3. **混淆不是加密**：它只改变代码形态（布局/数据/控制流），目标是让逆向成本高于收益；评估看 **potency / stealth / resilience / cost**。

**本章常见考法**

| 题型 | 典型问法 | 备考动作 |
|---|---|---|
| 画图 | 画栈帧，标出 buf/EBP/ret | 背“高地址→低地址”顺序 |
| 计算 | buf[64] 覆盖 ret 的偏移、payload 字节 | 会算 64+4，会小端写地址 |
| 防御分析 | NX/canary/ASLR 各防什么、怎么绕过 | 一张表背下来 |
| 概念 | 混淆三类、四个评估维度 | 每类举 2 个例子 |
| 设计 | 为什么混淆不能彻底防 RE | 答“成本 + Kerckhoffs + 有限搜索空间” |

## 1. 缓冲区溢出（buffer overflow）

### 1.1 漏洞谱系与“可利用性”★

可能被利用的 bug（课件列举）：

- 空指针解引用、UAF、double free、数组越界、栈/堆溢出；
- 返回局部变量指针、未初始化变量、负数误用；
- 大参数按值传递、分配不足；
- 内存/文件句柄/网络资源泄漏、未处理返回码、失效迭代器。

> ⚠ **并非所有 bug 都可利用**；不可利用的逻辑 bug 不构成 vulnerability。常见高危：**buffer overflow、format string、integer overflow、UAF、type confusion、race condition**。

### 1.2 进程内存布局 ★★

```
高地址
┌──────────────┐
│ stack        │ ← 向低地址增长
├──────────────┤
│              │
├──────────────┤
│ heap         │ ← 向高地址增长
├──────────────┤
│ bss          │ 未初始化全局/静态
├──────────────┤
│ data         │ 已初始化全局/静态
├──────────────┤
│ text         │ 代码
└──────────────┘
低地址
```

- Mac/Windows 类似；具体地址随机化（ASLR）会改变基址。
- 栈帧（32-bit，简化，忽略对齐填充）：

```
高地址
┌─────────────────┐
│ 参数 a, b        │
├─────────────────┤
│ 返回地址 ret     │ ← 溢出目标（4 字节）
├─────────────────┤
│ saved EBP        │ ← 4 字节
├─────────────────┤
│ 局部变量         │
│ char buf[64]     │ ← 写入起点，向高地址写
└─────────────────┘
低地址              ESP
```

- 函数调用时压入返回地址、帧指针、局部变量；**栈向低地址增长，缓冲区向高地址写** → 溢出先覆盖 saved EBP，再覆盖 **ret**。

### 1.3 两种“越界”★

| 类型 | 行为 | 后果 | 例子 |
|---|---|---|---|
| **Buffer overread** | 读超出缓冲区 | 泄露相邻内存（可绕过 ASLR） | **Heartbleed**（OpenSSL 读越界） |
| **Buffer overwrite** | 写超出缓冲区 | 篡改相邻数据/返回地址 | 栈溢出、堆溢出 |

### 1.4 溢出攻击原理 ★★

**最简单的场景**：`char buffer[N]` 旁边有 `boolean flag`（口令正确标志）；超长输入覆盖 flag → 任意口令通过。

**栈溢出**：

1. 覆盖 ret → 程序“返回”到错误地址 → 崩溃（DoS）；
2. 更坏：让 ret 指向**注入的恶意代码**（shellcode）→ 任意代码执行；
3. 别名：stack smashing、buffer overrun、**code injection**、**control-flow hijacking**。

**前提**：
- 代码中确实存在溢出；
- **并非所有溢出都可利用**；
- 常需 trial-and-error 猜地址，但“成功一次就够”。

> ⚠ “让缓冲区向高地址增长”并不能解决问题（课件注明见笔记）——因为 ret 仍在缓冲区的“上方”，只是覆盖方向变了，攻击者仍可构造布局。

### 1.5 不安全的 C 库函数 ★

| 函数 | 问题 |
|---|---|
| `strcpy(dest, src)` | 不检查 dest 长度 |
| `gets(s)` | 完全不知道缓冲区大小 |
| `strcat(dest, src)` | 追加时可能越界 |
| `scanf("%s", ...)` | 不限制宽度 |
| `sprintf(buf, ...)` | 格式化输出可能超长 |

> 共同点：**不检查目标缓冲区长度**；应使用 `strncpy`/`snprintf`/`fgets` 等带长度参数的版本，并检查返回值。

### 1.6 利用步骤（serial 案例）★★

**场景**：程序要求 serial，不知道正确值，只有 exe；错误则退出。

1. **探测偏移**：输入递增长度的 `A`（0x41），观察崩溃时 ret 是否被 `0x41414141` 覆盖 → 确定偏移。
2. **找目标地址**：反汇编，找到“跳过检查”的地址（如 `0x401034`）。
3. **按小端写地址**：`0x401034` → 字节 `34 10 40 00` → ASCII `4^P@`。
4. **构造 payload**：`填充 + 目标地址`（必要时加 NOP sled + shellcode）。
5. **触发**：程序返回时跳到目标地址，绕过检查。

**偏移计算（32-bit 简化）**：

```
char buf[64];
偏移(ret) = 64 (buf) + 4 (saved EBP) = 68
payload = b"A"*68 + p32(target)
```

> 若目标地址含 `0x00`，`strcpy` 会被截断 → 实际利用要选不含空字节的地址（如 `0x0804a080` → `\x80\xa0\x04\x08`），或用其他写入方式。

**NOP sled**：在 shellcode 前放大量 `0x90`，只要 ret 落进 sled 任一位置就能滑到 shellcode，降低“精确猜地址”的难度。

### 1.7 防御 ★★

| 防御 | 机制 | 能防什么 | 局限/绕过 |
|---|---|---|---|
| **W^X / DEP** | 栈/堆标记为不可执行（write XOR execute） | 栈上 shellcode 直接执行 | **ROP/return-to-libc** 复用已有代码；JIT/自修改代码需要可写可执行内存 |
| **Canary（栈金丝雀）** | 在局部变量与 saved EBP 之间放一个随机值；函数返回前检查 | 连续栈溢出（必须破坏 canary 才能到 ret） | 可**泄露 canary**（格式化字符串/信息泄露）；任意写可不碰 canary；非万无一失；约 8% 性能损失 |
| **ASLR** | 随机化栈、堆、库、可执行文件基址 | 让攻击者猜不中地址 | 32-bit 熵低可暴力猜；可 **spraying**；需 info leak 配合；不防“不依赖固定地址”的攻击 |
| **安全语言** | Java/C#/Rust 等自动边界检查 | 从根上消除越界 | 需重写/迁移；性能、兼容性、FFI |
| **安全函数** | 带长度参数的库函数 + 检查 | 减少常见错误 | 依赖开发者正确使用；逻辑错误仍在 |

**Canary 细节**

- 经典常量 `0x000aff0d`（含 `\x00`、`\x0a`、`\xff`、`\x0d`，防止被字符串函数无意复制）；也可运行时随机。
- 函数序言写入，函数尾声比较；不一致 → `__stack_chk_fail` → 终止。
- 绕过：先泄露 canary 再原样写回；或利用不经过栈的写原语。

**ASLR 细节**

- 攻击者可以**重复猜**（尤其 32-bit 地址空间小）；可以**喷射**大量攻击代码提高命中率。
- 与 NX 组合后，攻击者转向 ROP：用已有代码片段（gadget）拼出攻击逻辑。

> 现代组合：**ASLR + canary + NX + PIE + CFI**；没有单一防御足够。

### 1.8 为什么“缓冲区反向增长”不是解法

- 若缓冲区向高地址增长，ret 在低地址侧，看似不会被覆盖；
- 但攻击者可以覆盖其他关键数据（函数指针、saved EBP、参数），或利用堆/其他结构；
- 根本问题是**缺少边界检查**，不是增长方向。

## 2. 软件混淆（obfuscation）

### 2.1 动机与威胁模型 ★

- 软件含大量信息：.NET 的 MSIL、Java/JS/Python 字节码、C/C++ 二进制。
- 代码会被利用：
  - 非恶意 RE：测试、集成、扩展；
  - 恶意 RE：攻击、盗版、抄袭；
  - 恶意软件作者也想逃避**聚类/相似性分析**。
- **移动代码 + 恶意主机**：代码在别人的机器上运行，宿主不可信 → 需要“软件保护”。

### 2.2 为什么现有保护不够 ⚠

| 方案 | 问题 |
|---|---|
| 硬件隔离 | 需改造硬件，不现实 |
| 服务器端执行 | 需始终在线高带宽；还要解决认证等网络安全问题 |
| 加密 | **鸡生蛋**：解密例程本身可见，攻击者总能拿到解密后的代码 |

### 2.3 目标与边界 ★

- 混淆：让被保护软件“看起来”与原版不同；**判断两段代码的相似性**是许多软件安全分析的基础。
- **不能完全阻止**恶意 RE：给定足够时间/资源，任何混淆都可被还原（穷举）。
- 正确目标：**让还原成本对攻击者而言过高**（提高成本，而不是追求绝对安全）。

### 2.4 三类混淆 ★★

#### （1）Layout obfuscation（布局）

- 删除注释、重命名标识符（类/方法/变量 → 无意义名）。
- 工具：DashO（Java）、Dotfuscator（MSIL）。
- 特点：**非常轻量**，不改变语义；现实中大量流行 App 甚至没做布局混淆。

#### （2）Data obfuscation（数据）

- 变量拆分/合并/编码。
- 数组拆分、数组合并、数组折叠（增维）、数组展平（降维）。
- 数据加密（如字符串加密，移动 App 常用）。
- 目的：让“数据是什么、怎么用”更难推断。

#### （3）Control-flow obfuscation（控制流）★

**前提**：布局/数据混淆不改变控制结构 → 控制结构仍可作“代码签名”。

**手段 1：指令插入（垃圾代码）**

- 插入无语义指令：`nop`；或语义抵消序列：`add → sub`、`xor → xor`。
- 优点：简单、易实现、破坏已知模式/签名。

**手段 2：指令替换**

- 用等价指令序列替换原指令。
- 极端案例：**M/o/Vfuscator** 把 C/C++ 编译成“只有 `mov` 指令”的程序。

**手段 3：控制流平坦化（flattening）**

- 把函数的所有基本块放进一个 `switch(x)` 分发器，用状态变量 x 驱动。
- 原 CFG 被“压平”，丢失明显的分支/循环结构。

例：函数 `f(i,j)`：`a=1; if(i<j) a=j; do { a*=i--; } while(i>0); return a;`

| 原基本块 | 平坦化后的状态 |
|---|---|
| A: `a=1` | `x=0` → case 0: A; `x = (i<j) ? 1 : 2` |
| B: `a=j` | case 1: B; `x=3` |
| C: `a=a*i; i=i-1` | case 2: C; `x = (i>0) ? 2 : 3` |
| D: `return a` | case 3: D |

外层只留一个 `while(true) switch(x)`。

**手段 4：不透明谓词（opaque predicate）**

- 条件表达式的值在运行时**已知**，但静态分析难以推断。
- 例：`if (x*x + y*y >= 2*x*y)` 恒真，因为 \((x-y)^{2} \ge 0\)；汇编中更不直观。
- 类型：
  - **Invariant**：恒真/恒假，与输入无关；
  - **Context**：只在特定上下文成立；
  - **多线程**：一个线程只往全局结构放 `>n` 的数，另一个线程取一个赋给 x → `if (x<n)` 恒假。
- 不透明性决定控制流变换的**韧性**。

**进阶**

- **VM-based obfuscation**：自定义指令集 + 秘密编码 + 虚拟 CPU/分发器；已商业化；不是万无一失，但显著增加分析难度。
- **Multilingual obfuscation**：混合不同计算模型（命令式=图灵机、函数式=lambda 演算、逻辑式=Horn 逻辑），编译后机器码更难理解。

### 2.5 混淆效果评估 ★★

| 维度 | 含义 | 度量 |
|---|---|---|
| **Potency** | 引入多少复杂度 | 调用图边数、基本块数、CFG 边数等 |
| **Stealth** | 混淆代码能否“融入”其余代码 | 指令分布异常检测 |
| **Resilience** | 还原有多难 | diff 技术比较混淆前后二进制相似度 |
| **Cost** | 性能代价 | 体积、执行减速 |

> 四者需要权衡：potency 高可能 cost 大；stealth 好可能 resilience 低。

### 2.6 为什么“好”的混淆很难设计 ⚠

- 想出“有趣”的变异不难，需要创造力；想出“安全”的变异极难。
- 尤其当方法公开、攻击者已知你的方案时（**Kerckhoffs 的延伸**）。
- 开放设计 + 无真正秘密 + 搜索空间有限 → 原理上就不强。

## 3. 例题精讲

### 例 1：ret 偏移（8 分）

**题**：32-bit 程序，函数内 `char buf[64]`，无对齐填充，saved EBP 4 字节，ret 4 字节。覆盖 ret 需要多少字节填充？

**解**：
- buf 64 字节；
- saved EBP 4 字节；
- 因此 ret 从 buf 起始的第 **68** 字节开始；
- payload = `b"A"*68 + p32(target)`。

**得分点**：说明“先覆盖 saved EBP，再覆盖 ret”；提到实际编译器可能有对齐填充，需动态确认。

### 例 2：小端 payload（8 分）

**题**：目标地址 `0x0804a080`，写出 payload 中的地址字节。

**解**：
- little-endian：低字节在前 → `80 a0 04 08`；
- Python：`p32(0x0804a080)` = `b"\x80\xa0\x04\x08"`。
- 若地址含 `\x00`（如 `0x08048400`），`strcpy` 会截断，需换地址或换写入方式。

### 例 3：canary 原理（8 分）

**题**：canary 如何检测栈溢出？攻击者如何绕过？

**解**：
- 编译器在局部变量与 saved EBP 之间放一个随机值；函数返回前比较该值是否被改；不一致则调用 `__stack_chk_fail` 终止。
- 连续溢出必须经过 canary 才能到 ret，因此会被发现。
- 绕过：① 泄露 canary 后原样写回（格式化字符串/信息泄露）；② 使用不经过该栈帧的任意写；③ 覆盖不触发检查的路径。

### 例 4：ASLR 的局限（8 分）

**题**：ASLR 随机化地址，为什么 32-bit 程序仍可能被绕过？

**解**：
- 32-bit 地址空间熵有限，攻击者可**暴力猜**（反复试，崩溃重启）；
- 可用 **heap/stack spraying** 大量布置攻击代码/ROP gadget，提高命中率；
- 需要 info leak 泄露基址；或转向不需要固定地址的攻击（如 partial overwrite）。
- 因此 ASLR 必须与 NX、canary、CFI 等组合。

### 例 5：控制流平坦化（10 分）

**题**：把 `a=1; if(i<j) a=j; do{a*=i--;}while(i>0); return a;` 用 switch 分发器平坦化。

**解**：

```
x = 0;
while (1) {
  switch (x) {
    case 0: a = 1; x = (i < j) ? 1 : 2; break;
    case 1: a = j; x = 3; break;
    case 2: a = a * i; i = i - 1; x = (i > 0) ? 2 : 3; break;
    case 3: return a;
  }
}
```

- 原 CFG 的分支/循环被“藏”进状态变量 x 的赋值中；静态分析要先恢复 x 的取值才能重建 CFG。

### 例 6：不透明谓词（6 分）

**题**：`if (x*x + y*y >= 2*x*y)` 为什么恒真？有什么前提？

**解**：
- \(x^{2} + y^{2} - 2xy = (x-y)^{2} \ge 0\)；
- 因此对任意实数 x、y 恒真；汇编中不易看出。
- 前提：整数运算不溢出；若溢出则可能为假（设计时要考虑）。

### 例 7：混淆评估（8 分）

**题**：某混淆器让程序体积增大 3 倍、运行慢 40%，但指令分布与正常代码差异明显。用四个维度评价。

**解**：
- **Cost**：差（体积 3×、慢 40%）；
- **Stealth**：差（指令分布异常，易被统计检测）；
- **Potency**：需要看 CFG/基本块复杂度是否真的提高；
- **Resilience**：需要做 diff/相似性分析，看还原难度。
- 结论：该混淆“视觉上复杂”，但 stealth 和 cost 不理想，整体效果有限。

## 4. 易错点（考场最易丢分）

| 错误 | 正确 |
|---|---|
| 栈向高地址增长 | 栈向**低地址**增长；缓冲区写入向高地址 |
| 溢出一定覆盖 ret | 可能只覆盖局部变量/EBP；要看布局和长度 |
| 所有溢出都可利用 | 很多只导致崩溃；可利用性取决于布局、地址、保护 |
| NX 能防所有代码执行 | 防“栈上执行”；ROP/return-to-libc 可绕过 |
| canary 万无一失 | 可泄露/绕过；不保护非连续写 |
| ASLR 让攻击不可能 | 32-bit 可暴力猜；可 spray；需 info leak |
| 用安全函数就安全 | 逻辑错误、长度计算错误仍在 |
| 混淆 = 加密 | 混淆不保密，只增加理解成本；加密有密钥 |
| 混淆能彻底防 RE | 不能；只能提高成本 |
| Potency 越高越好 | 还要看 stealth/resilience/cost 的权衡 |
| 控制流平坦化改变了程序语义 | 不改变；只是把 CFG 藏进状态变量 |

## 5. 自测（先做，再看答案）

1. 画出 32-bit 栈帧，标出参数、ret、saved EBP、buf 的顺序。
2. 为什么溢出能覆盖返回地址？栈的增长方向是什么？
3. overread 和 overwrite 的区别？Heartbleed 属于哪种？
4. 列举 5 个不安全的 C 库函数，并说明共同问题。
5. 描述栈溢出的完整利用步骤；NOP sled 的作用？
6. W^X、canary、ASLR 各防什么？各有什么局限？
7. 为什么“让缓冲区向高地址增长”不能解决问题？
8. 混淆的三类是什么？各举两个具体手段。
9. 控制流平坦化的原理？不透明谓词的本质？
10. 混淆效果从哪四个维度评估？为什么“安全混淆”很难？
11. VM-based 混淆和 multilingual 混淆各是什么？

### 答案

1. 高→低：参数、ret、saved EBP、局部变量（buf 在最靠近 ESP 的低地址端）。
2. 栈向低地址增长，buf 向高地址写；ret 位于 buf 上方，超长写入会先过 saved EBP 再到 ret。
3. overread 读越界（泄露），overwrite 写越界（篡改）；Heartbleed 是 overread。
4. `strcpy`、`gets`、`strcat`、`scanf("%s")`、`sprintf`；都不检查目标缓冲区长度。
5. 探测偏移 → 找目标地址 → 小端写地址 → 构造 payload（填充+地址，可加 NOP sled/shellcode）→ 触发返回。NOP sled 降低猜地址精度要求。
6. W^X：栈不可执行，防 shellcode；可被 ROP 绕过。canary：检测连续溢出；可泄露/绕过。ASLR：随机化地址；32-bit 可暴力猜、可 spray。
7. 根本问题是缺边界检查；ret 仍可通过其他布局/结构被覆盖，或改函数指针/参数。
8. 布局（重命名、删注释）；数据（数组拆分/合并、字符串加密）；控制流（垃圾指令、指令替换、平坦化、不透明谓词）。
9. 把所有基本块放进 switch 分发器，用状态变量驱动；不透明谓词是“运行时值已知、静态难推断”的条件。
10. Potency、Stealth、Resilience、Cost；因为方法公开（Kerckhoffs）、无真正秘密、搜索空间有限，攻击者可针对性还原。
11. VM-based：自定义指令集 + 虚拟 CPU 解释执行；multilingual：混合命令式/函数式/逻辑式等不同计算模型。

## 6. 考前速记卡

| 项目 | 内容 |
|---|---|
| 栈方向 | 栈向低地址增长；buf 向高地址写 |
| 32-bit 栈帧 | 参数 / ret / saved EBP / buf（低地址） |
| 偏移 | `buf[64]` → ret 偏移 68（64+4） |
| 小端 | 低字节在前；`0x0804a080` → `80 a0 04 08` |
| 危险函数 | strcpy、gets、strcat、scanf、sprintf |
| 别名 | stack smashing、code injection、control-flow hijacking |
| W^X | 栈不可执行；绕过：ROP/return-to-libc |
| Canary | `0x000aff0d` 或随机；约 8% 开销；可泄露 |
| ASLR | 随机化基址；32-bit 熵低；可 spray/暴力猜 |
| 混淆三类 | layout / data / control-flow |
| 控制流手段 | 垃圾指令、指令替换（mov-only）、平坦化、不透明谓词 |
| 不透明谓词 | \((x-y)^{2}\ge 0\)；invariant/context/多线程 |
| 评估 | potency / stealth / resilience / cost |
| 边界 | 混淆只提高成本，不能彻底防 RE |
